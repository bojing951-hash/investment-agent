## 5.1 根因决策门(7.1)

**每个问题进入开发前必须先过此门**,决策记录登记于 RDG-REGISTRY.md:
```
根因决策记录(RDG-<date>-<n>)
问题:              <一句话,含真实故障证据链接>
根因分类(三选一,须附证据):
  □ 局部实现错误(Bug)     → 证据: <复现输出/日志行>
  □ 接口或架构缺陷          → 证据: <≥2 起同类故障/跨模块同因>
  □ 根因证据不足            → 证据: <已排除项清单>
处置(按分类强制):
  Bug          → 最小修复(禁顺手重构;diff 面积≈根因面)
  架构缺陷     → 先改设计档(契约/接口)再改实现;实现 diff 须映射设计 diff
  证据不足     → 诊断实验先行(可证伪假设+判据),禁直接大规模重构
回看(修复后填): 分类是否正确?误判成本?
```

**判例纪律**: 三起真实故障(状态漂移/Gate B 误杀/提取器缺陷)=判例库
首三条,均为「正则/文本猜义类架构缺陷」而非 Bug,处置=本整改(先契约后
实现),不是继续加正则例外。

## 5.2 优先级公式(7.2)

**优先级分 = 真实用户影响 × 错误严重程度 × 复发概率 × 架构根因度 × (1/修复成本)**

| 因子 | 取值锚(1-5) |
|---|---|
| 真实用户影响 | 5=LIVE 周报/公开仓错误读者可见;3=内部研究结论错;1=无人消费的档 |
| 错误严重程度 | 5=金融数值错误发布;3=误杀阻断正确报告;1=措辞/文档 |
| 复发概率 | 5=同类已≥3 起;3=机制性必现条件已知;1=一次性环境巧合 |
| 架构根因度 | 5=契约层缺失(身份/单位/时间语义);3=接口不一致;1=局部笔误 |
| 修复成本(反比) | 5=<1 文件局部;3=多文件+测试;1=跨系统迁移 |

**明令废除的分母**: Bug 数/文件改动数/Commit 数/测试数量/Charter 完成
数不得作为优先级输入。每轮任务入选须给五因子打分存档;同分冲突时
**架构根因度高者先**(止血让位于断根)。

## 5.3 能力验收六问(7.3)

每轮结束**逐问作答,任一问无真实证据=该轮不得标能力 PASS**:

1. 本轮修复了什么根因?(→ 引用 5.1 决策记录编号)
2. 消除了哪一类错误?(→ 错误类名,须能在验收集构造反例)
3. 有什么真实证据证明?(→ 命令+输出摘录,禁只写结论)
4. 哪些场景仍可能失败?(→ 诚实清单,如 T7 FK-1..8)
5. 是否产生新的架构复杂度?(→ 新增模块/接口/例外计数;净增>0 须论证)
6. 下一轮最重要的能力差距是什么?(→ 引用 5.2 公式排序首位)

## 5.4 状态语义一致性(7.4)

**唯一权威研发状态** = `docs/autonomous-rd/CURRENT_STATE.md`。恢复/每轮
开班必检七项(检查器可执行,不只人读;R20 六项底座+⑦ 扩展):

| # | 检查 | 机器门 |
|---|---|---|
| 1 | Git HEAD 与状态档记载一致 | rd_state_consistency ① |
| 2 | 实际合并状态一致 | ①(容忍类核验)+②检查点块 |
| 3 | 最新完成轮次一致 | ②⑤(轮次关系纪律) |
| 4 | 当前任务一致 | ②next_task+③台账 |
| 5 | 已完成任务可复核 | ③证据列+⑤completed_ids |
| 6 | 未解决问题清单活 | ②RESUME 活动区纪律 |
| 7 | 最终验收状态如实 | ⑦a PASS 行证据形态+⑦b 根因门 |

**规则**: 只验证 Git 祖先关系不算核验——必须核「状态文件描述的现实」与
仓库/研发记录一致;不一致→先修状态再继续(章程§十);新会话恢复前必跑
此检查。
